# Agentforce Tracing and Analytics
## Study Guide

---

## Section 1: Observability Foundations

### Objective 1.1: Understand why observability is essential for AI agents and how it differs from traditional software monitoring.

---

**Topic:** Why AI agents require a different observability approach than deterministic software

**Explanation:** Traditional software is deterministic: given the same input, it produces the same output every time, making unit tests a reliable coverage mechanism. AI agents are probabilistic. The language model's response varies based on how a user phrases a request, the conversation history, the clarity of the agent's instructions, and model behavior that is not fully predictable. An agent that works flawlessly in ten test sessions can fail for the eleventh user who phrases their request slightly differently. This gap between tested behavior and real-world behavior is exactly what observability tooling is designed to close. Best practices treat observability not as an optional post-launch activity but as a core requirement of any production agent deployment.

---

**Topic:** The three fundamental questions that Agentforce observability is designed to answer

**Explanation:** Practitioners deploying Agentforce agents at scale face three fundamental questions about every agent in production. First: Is the agent being used? This is the adoption question, answered through usage and volume analytics. Second: Is it working correctly? This is the quality question, answered through deflection rates, grounding results, and session-level traces. Third: Is it safe and healthy? This is the trust question, answered through health monitoring, safety scoring, and platform alerts. The three Agentforce observability pillars map directly to these three questions, and a complete observability strategy must address all three.

---

**Topic:** The risk of operating a production agent without observability tooling

**Explanation:** Without observability, an agent's behavior in production is unverifiable. The language model will generate confident-sounding responses regardless of whether the underlying action executed correctly. An agent can respond "I've updated your account" even if no record was written. An agent can present a high deflection rate on a dashboard even if many of those "deflected" sessions ended in graceful failures rather than genuine resolution. Best practices require observability tooling to be configured before go-live so that the team operates on evidence rather than assumption from the first production session onward.

---

### Objective 1.2: Identify and distinguish between the three Agentforce observability pillars.

---

**Topic:** Pillar I - Agent Analytics: the executive layer of observability

**Explanation:** The first observability pillar consists of pre-built, out-of-the-box dashboards and the underlying Data Cloud DMO tables that provide an aggregated view of how an agent performs across all sessions. Because it is not practical to manually review every conversation, analytics serve as an aggregated signal layer that surfaces trends, anomalies, and KPIs at a glance. This pillar answers the adoption question: how many users are engaging with the agent, which topics are being requested, and what percentage of sessions resolve without human escalation. It is the entry point for stakeholder reporting and early-adoption monitoring.

---

**Topic:** Pillar II - Agent Optimization: the deep inspection layer

**Explanation:** The second observability pillar provides session-level and service-level tooling for deep inspection of individual conversations and back-end execution chains. This is the layer a practitioner uses when they know something is wrong and need to identify the exact cause. It includes session trace files generated by the CLI preview tool, Agent Platform Tracing spans stored in Data Cloud, and custom evaluations that automate quality detection at scale. This pillar transforms the language model from a black box into a glass box by exposing exactly what the model received as input, what it decided to do, what data it used, and whether its response was grounded in real action output.

---

**Topic:** Pillar III - Health Monitoring: the real-time alerting layer

**Explanation:** The third observability pillar provides real-time alerting built on top of the Einstein Trust Layer's fail-safe infrastructure. While analytics dashboards show what happened historically, health monitoring surfaces what is happening right now, enabling a team to respond before a systemic issue affects a large number of users. Health monitoring covers platform-level alerts for escalation rate spikes, error volume thresholds, LLM latency breaches, and session initialization failures. It also tracks integration health including Flow execution timeouts, Apex callout failures, and Data Cloud indexing lag for knowledge-grounded agents. Best practices recommend configuring all alert thresholds before a production go-live.

---

### Objective 1.3: Distinguish between the two tracing systems and know when to use each one.

---

**Topic:** Session Tracing vs. Agent Platform Tracing: understanding the two layers

**Explanation:** Agentforce provides two separate tracing systems that operate at different layers of the execution stack. Session Tracing operates at the planner (conversational) level and captures user input, subagent routing decisions, agent responses, and grounding results. Its primary DMO is `ssot__AiAgentInteraction__dlm`, and it is enabled by default when Data Cloud is provisioned. Agent Platform Tracing operates at the service (back-end execution) level and captures individual LLM calls, Flow runs, Apex invocations, duration timings, errors, and span-level attributes. Its primary DMO is `ssot__TelemetryTraceSpan__dlm`, and it must be explicitly enabled in Setup. Using the analogy from Salesforce documentation: Session Tracing is the conversation transcript; Platform Tracing is the execution log of every system call that powered each line of that transcript. Both layers are required for complete observability.

---

**Topic:** The primary diagnostic question answered by each tracing system

**Explanation:** Session Tracing is the right tool when the diagnostic question is "What did the agent decide?" It reveals which subagent handled a turn, what instructions the LLM received, what actions were available and which ones fired, and whether the response passed grounding validation. Agent Platform Tracing is the right tool when the diagnostic question is "Why did it take that long?" or "Where exactly did it break?" It reveals the full hierarchical chain of back-end calls with individual span durations and status codes, enabling a practitioner to pinpoint a slow Apex query, a Flow that returned zero rows, or an external service that timed out. Conflating the two systems leads to using the wrong tool for a given diagnosis.

---

**Topic:** How Session Tracing and Platform Tracing are joined for end-to-end analysis

**Explanation:** The two tracing systems are designed to be joined. The field `ssot__TelemetryTraceId__c` on `ssot__AiAgentInteraction__dlm` (Session Tracing) corresponds to the field `ssot__TelemetryTrace__c` on `ssot__TelemetryTraceSpan__dlm` (Platform Tracing). This join allows a practitioner to start from a known interaction in the session trace and pull the complete back-end execution chain that powered it. The full data hierarchy from outer to inner is: Session, then Interaction, then Step, then Span, with each Span potentially having child Spans. Best practices recommend a two-step SOQL approach: first retrieve the `TelemetryTraceId` from the interaction record, then query all spans matching that trace ID ordered by start time to reconstruct the execution chain.

## Section 2: Infrastructure Prerequisites

### Objective 2.1: Identify and verify the infrastructure components required before any observability feature functions.

---

**Topic:** Data Cloud (Data 360) as the mandatory foundation for all observability features

**Explanation:** Both Agentforce Session Tracing STDM tables and Agent Platform Tracing DMOs store their data in Data Cloud (also called Data 360). Neither feature works without Data Cloud provisioned and active in the org. A common diagnostic failure mode is finding an org where dashboards are visible but surface no data because Data Cloud was never configured. The standard verification approach is to run a SOQL query against `DataKnowledgeSpace`: if this returns an `INVALID_TYPE` error, Data Cloud is not provisioned. When that is the case, the practitioner should direct the customer to Setup > Data Cloud Setup and verify that the CRM Connector is active before proceeding with any observability configuration. This step cannot be skipped.

---

**Topic:** Enabling Agent Platform Tracing and the critical no-backfill constraint

**Explanation:** Agent Platform Tracing is disabled by default in every Salesforce org and must be explicitly toggled on in Setup > Agent Platform Tracing. Span data begins populating within minutes of the first Agentforce action execution after enablement. The most important constraint to understand is that there is no retroactive backfill: any agent sessions that occurred before the toggle was enabled are permanently invisible to Platform Tracing. Salesforce documentation and best practices both treat this as a critical deployment prerequisite, recommending that Platform Tracing be enabled as early as possible in every customer engagement, ideally before any production sessions occur.

---

**Topic:** Required permission sets for querying trace DMOs and why missing permissions are easy to misdiagnose

**Explanation:** Users who query trace DMOs need explicit access grants configured through permission sets. The key permission sets include `Data Cloud Data Access` for read access to DMOs, `CopilotSalesforceAdmin` for access to Agentforce Studio and agent APIs, `GenieAdmin` for Data Cloud administration, `AgentforceServiceAgentUser` for the Einstein Agent runtime user, and either `GenieUserEnhancedSecurity` or `DataCloudUser` for knowledge-grounded agents. The critical diagnostic pitfall is that missing permissions produce empty query results rather than error messages. A practitioner who has not assigned the correct permissions will run a SOQL query, receive zero rows back, and may incorrectly conclude that no data exists. Best practices recommend verifying permission set assignments as the first step whenever a trace DMO query returns unexpectedly empty results.

---

**Topic:** Infrastructure readiness checklist for a new org before enabling observability

**Explanation:** Before considering any observability configuration complete in a new org, Salesforce best practices recommend verifying the following: Data Cloud is provisioned and the `DataKnowledgeSpace` query succeeds without errors; the `CopilotSalesforceAdmin` permission set is assigned to the admin user; the `GenieAdmin` permission set is assigned to the admin user; the `Data Cloud Data Access` permission set is assigned to any user who will query DMOs; Agent Platform Tracing has been toggled on in Setup; Einstein Trust Layer Audit Trail data streams are enabled if compliance logging is required; and alert thresholds are configured before the production go-live date. Skipping any of these steps is the most common source of "observability is configured but surfacing no data" support issues.

## Section 3: Session-Level Tracing and Debugging

### Objective 3.1: Understand how to run and interpret CLI-based session traces during development and validation.

---

**Topic:** The foundational rule of Agentforce debugging: the trace is ground truth, not the agent's response

**Explanation:** The single most important principle in Agentforce debugging is that the agent's text response is never evidence that an action executed. A language model will generate confident-sounding responses describing successful outcomes even when no underlying action was invoked. An agent may say "I have created your support case" even if the `FunctionStep` for the case-creation action does not appear anywhere in the trace. This is not a platform defect; it is an inherent property of language model generation. Best practices require practitioners to verify agent behavior by reading trace files rather than by reading the conversation transcript. The trace is the authoritative source of truth about what actually executed at the system level.

---

**Topic:** Simulated preview mode vs. live preview mode: when to use each

**Explanation:** The CLI preview tool supports two execution modes. In simulated mode (using the `--simulate-actions` flag), the language model generates fake action outputs and no real Apex, Flow, or Prompt Template code executes. This mode is appropriate during early development when the backing code does not yet exist, and it avoids the credit consumption of live action execution. In live mode (using the `--use-live-actions` flag), real code executes and real data is used. Live mode is required for validating grounding, verifying variable-driven branching, and confirming that actions return expected data shapes. Grounding failures identified in simulated mode may be false positives because the LLM-generated fake outputs do not match real data patterns. Best practices recommend switching to live mode before diagnosing any grounding failure.

---

**Topic:** How trace files are structured and how to connect a failing turn to its trace

**Explanation:** Each turn in a preview session generates a separate JSON trace file stored in `.sfdx/agents/<AgentName>/sessions/<SESSION_ID>/traces/<PLAN_ID>.json`. The trace file has three principal components: top-level metadata including the `planId`, `sessionId`, detected intent, and which subagent handled the turn; the `plan` array containing the ordered list of execution steps; and the `transcript.jsonl` file in the session directory, which links each agent turn to the `planId` of its corresponding trace file. To diagnose a failing turn, the practitioner first reads the `transcript.jsonl` to identify the `planId` for that specific turn, then opens the corresponding trace file. Traces are written after every message sent, not only at session end, so mid-session inspection is possible.

---

**Topic:** The complete set of step types in an Agentforce trace and what each reveals

**Explanation:** Agentforce session traces contain a fixed vocabulary of step types, each revealing a specific layer of execution. `UserInputStep` records the exact utterance that triggered the turn. `SessionInitialStateStep` shows the full variable state at turn start. `NodeEntryStateStep` identifies which subagent is executing and provides a state snapshot. `VariableUpdateStep` records when a variable changed, including old and new values. `BeforeReasoningIterationStep` confirms that deterministic pre-processing actions fired. `EnabledToolsStep` lists every action that was visible to the LLM for this reasoning cycle; if an expected action is absent from this step, it cannot fire. `LLMStep` contains the full prompt sent to the model, available tools, and the model's decision. `FunctionStep` records that an action actually executed, with its inputs, outputs, and latency. `ReasoningStep` provides the grounding check result. `TransitionStep` records subagent routing. `PlannerResponseStep` contains the final response delivered to the user including safety scores. Each step type has a distinct diagnostic purpose, and reading traces end-to-end in this order surfaces root causes efficiently.

---

**Topic:** The LLMStep: the most diagnostic step in any trace

**Explanation:** The `LLMStep` is the single most valuable step in an Agentforce session trace because it exposes the complete input that the language model received and the decision it made in response. The `messages_sent` field contains the full compiled prompt including Agent Script instructions, conversation history, variable interpolations, and platform-injected system content. When an agent makes an unexpected decision, the root cause is almost always visible in this field. The `tools_sent` field lists the action names that were available to the model during this reasoning cycle. The `response_messages` field shows the model's decision: either a natural language reply or a tool invocation request. The `execution_latency` field records the LLM call duration in milliseconds, which is the primary diagnostic signal for voice agent latency problems where the sub-2-second response window is the target. Best practices recommend starting every trace review with the `LLMStep` before examining any other step.

---

### Objective 3.2: Understand grounding validation and how to prevent and diagnose grounding failures.

---

**Topic:** What grounding is and why it functions as a quality gate on every agent response

**Explanation:** Grounding is the mechanism by which Agentforce validates that an agent's response is actually supported by the data returned from an action. After an action executes and returns data (captured in a `FunctionStep`), the agent composes a response using that data. The grounding checker then compares the agent's response against the action's output. If the response contains information that cannot be traced back to the action output, the grounding check fails with a status of `UNGROUNDED`. A `GROUNDED` result means the response accurately reflects the action data. A single `UNGROUNDED` result causes the platform to inject an error message and give the model a second attempt. Two consecutive `UNGROUNDED` results cause the agent to deliver a terminal error message to the user. Best practices treat grounding as a core quality signal, not an edge case.

---

**Topic:** The most common causes of grounding failures and how to recognize each

**Explanation:** Salesforce best practices identify four recurring causes of grounding failures. Date inference failures occur when an action returns a specific date string like "2025-02-19" but the agent responds with a relative term like "today"; the grounding checker cannot verify that the relative term maps to the exact date. Unit conversion failures occur when an action returns a precise value like "48.5F" but the agent rounds it to "about 50 degrees"; the checker does not recognize rounding as equivalent. Embellishment failures occur when the agent adds descriptive detail that did not appear in the action output, such as commenting on weather conditions when the action only returned temperature. Loose paraphrasing failures occur when the agent restates action output in language that diverges semantically from the source, creating a gap the checker flags as ungrounded. All four causes share a common pattern: the agent generates content that goes beyond what the action explicitly returned.

---

**Topic:** Writing grounding-safe instructions to prevent failures before they occur

**Explanation:** The most reliable way to prevent grounding failures is to write reasoning instructions that explicitly direct the agent to use action output values verbatim rather than paraphrasing or inferring from them. Best practices distinguish between two instruction patterns. The unsafe pattern permits paraphrasing by using vague directives such as "Tell the user about the weather." The safe pattern specifies verbatim usage: instruct the agent to use the exact date and temperature values returned by the action, to not paraphrase dates or round temperatures, and to quote action output values directly. Explicit references using `{{!@actions.ActionName}}` syntax in the instructions also help the language model associate the correct action with the relevant response task, improving both action selection and grounding compliance.

---

### Objective 3.3: Apply testing best practices for session-level validation.

---

**Topic:** Isolation-first debugging: testing actions before testing the full agent path

**Explanation:** When diagnosing an action that is not producing expected results, best practices recommend testing the backing Flow or Prompt Template in isolation before testing it within the full agent execution path. The full agent path introduces confounding variables including subagent routing decisions, variable state compilation, instruction resolution, and language model non-determinism. Testing in isolation via Prompt Builder or Flow debug mode removes all of these variables and confirms whether the underlying code is correct before attributing the problem to agent configuration. This principle applies to all action types including Apex, Flow, and Prompt Template actions.

---

**Topic:** Bi-directional state sync validation in multi-subagent architectures

**Explanation:** In agents that use multiple subagents, variables must flow correctly in both directions: from the router subagent down to child subagents, and from child subagents back up to the router. Best practices require validating both directions explicitly during testing. For the router-to-subagent direction, confirm that variables set by the router appear in the child subagent's `NodeEntryStateStep` with the correct values when the trace is examined. For the subagent-to-router direction, confirm that variables updated by a child subagent appear in the router's `VariableUpdateStep` when the child subagent completes and control returns. Skipping this validation is a common source of production failures where a child subagent has the data it needs but the router cannot access it for downstream routing or response logic.

---

**Topic:** Writing effective test utterances for agent preview sessions

**Explanation:** The quality of a preview test session is only as good as the quality of the utterances used to drive it. Salesforce best practices contrast ineffective keyword-style utterances with effective natural language utterances. Keyword-style utterances such as "cancel" or "order status" do not represent how real users phrase requests and can produce misleadingly positive routing results during testing while failing when real users engage. Natural language utterances such as "I've been thinking about it and I want to cancel my subscription" or "Can you look up where my package is? Order number is 12345" reflect actual user phrasing patterns and expose routing edge cases, instruction gaps, and grounding vulnerabilities that keyword tests miss. Best practices require test utterances to be phrased as complete natural language sentences before a go-live decision is made.

## Section 4: Agent Platform Tracing

### Objective 4.1: Understand how Platform Tracing works at the service level and how to interpret trace trees.

---

**Topic:** How Agent Platform Tracing captures back-end execution as a hierarchical trace tree

**Explanation:** Agent Platform Tracing stores every Agentforce action execution as an OpenTelemetry trace tree in Data Cloud. A single user utterance can trigger a cascade of downstream back-end calls including LLM steps, Flow executions, Apex invocations, and external service callouts. Platform Tracing captures all of these calls as a hierarchical tree of spans, where each span represents one step in the chain, has a status code (`OK` or `ERROR`), and records a duration in milliseconds. The parent-child relationships between spans are reconstructed by matching each span's `ssot__TelemetryParentSpanId__c` field to another span's `ssot__Id__c`. Spans with a null or zeroed parent ID are root spans. This tree structure enables a practitioner to see not just that something failed but exactly which step in the chain caused the failure and how long each step took.

---

**Topic:** Key fields on `ssot__TelemetryTraceSpan__dlm` and their diagnostic purpose

**Explanation:** The Agent Platform Tracing DMO `ssot__TelemetryTraceSpan__dlm` contains a specific set of fields that are used for all performance profiling and error analysis. `ssot__Id__c` is the unique span identifier used to reconstruct parent-child relationships. `ssot__TelemetryParentSpanId__c` identifies the parent span; a null or zeroed value marks the root span. `ssot__TelemetryTrace__c` is the trace ID that joins to Session Tracing via `ssot__TelemetryTraceId__c` on `ssot__AiAgentInteraction__dlm`. `ssot__OperationName__c` identifies the type of operation such as `run.llmstep`, `run.action.X`, or `run.invokeActions.FLOW`. `ssot__StatusCode__c` contains either `OK` or `ERROR`. `ssot__DurationNumber__c` records duration in milliseconds. `ssot__TelemetrySpanAttributeText__c` contains key-value attributes including `flow.api.name`, `db.rows_affected`, and `db.operation.name` which are essential for diagnosing data volume problems.

---

**Topic:** Why span attributes reveal diagnostic detail that the operation name does not

**Explanation:** A critical principle in reading Platform Tracing data is that the operation name on a span does not always accurately describe what the operation actually did. A span named with a "create record" pattern may, when its `db.operation.name` attribute is inspected, reveal that it performed a query rather than an insert. A span for a Flow action that completed with an `OK` status may show `db.rows_affected=0` in its attributes, indicating that the underlying SOQL query returned no results even though the Flow itself did not throw an exception. Without span attributes, a practitioner may assume an insert failed when in reality a lookup returned no matching data, leading to an incorrect remediation path. Best practices require reading span attributes alongside status codes and operation names to form accurate diagnostic conclusions.

---

**Topic:** Core SOQL patterns for performance profiling using Platform Tracing data

**Explanation:** Salesforce best practices provide several standard SOQL query patterns for diagnosing agent performance using `ssot__TelemetryTraceSpan__dlm`. The performance-by-operation-type query groups spans by `ssot__OperationName__c` and aggregates average and maximum duration along with span count, ordered by descending average duration. This is the first query to run when a customer reports that the agent "feels slow," because it immediately identifies which operation type is the consistent bottleneck. A second standard query filters by `ssot__StatusCode__c = 'ERROR'` to retrieve all recent error spans, and a count-by-operation-type variant identifies which steps are most failure-prone. A full trace reconstruction query filters by a specific `ssot__TelemetryTrace__c` value and orders results by `ssot__StartDateTime__c` ascending, producing the complete execution chain for a single interaction.

### Objective 4.2: Understand Slackbot integration as a conversational interface for trace analysis.

---

**Topic:** How Slackbot can be used for natural language trace queries

**Explanation:** Because Platform Tracing data lives in Data Cloud, it can be queried by any connected system including Slackbot. A practical implementation connects SOQL query patterns to a Slack canvas and exposes that canvas to Slackbot, enabling non-technical team members to ask trace analysis questions in natural language and receive structured trace tree results without writing SOQL directly. This pattern is valuable in enterprise environments where operations managers and support leads need trace visibility but are not SOQL practitioners. A Slackbot connection requires the org to have Agent Platform Tracing enabled, and the Slackbot must be provided with DMO schemas, sample query patterns, and join patterns via the Slack canvas at the start of each diagnostic session. This is a manual configuration step and is not automatically available.

## Section 5: MCP Actions and Observability Boundaries

### Objective 5.1: Understand how observability behavior changes when agents use MCP external actions.

---

**Topic:** What MCP actions are and how they differ from native Salesforce actions at the observability level

**Explanation:** Model Context Protocol (MCP) servers are registered external systems whose tools appear as callable actions in an Agentforce agent, routed via the `api://` or `externalService://` target protocol. From the agent's perspective they are invocable just like native Apex or Flow actions. However, the execution chain is different: instead of a Salesforce-managed invocation where the full execution stack is instrumented, the call goes to an external HTTP endpoint. This changes how observability behaves. Session Tracing records the action invocation in a `FunctionStep`, but the detail of the output depends on the MCP server's own logging. Platform Tracing captures spans only to the HTTP boundary; the internal execution of the MCP server is opaque to Salesforce instrumentation. Error attribution and latency profiling are therefore limited to what can be observed at the network boundary.

---

**Topic:** Identifying MCP action spans in a Platform Tracing trace tree

**Explanation:** In a Platform Tracing trace tree, MCP-backed actions can be identified by a specific span pattern. A native Apex or Flow action shows child spans under the invocation span that include detailed sub-steps such as `run.Flow.1` with `db.*` attributes. An MCP action instead shows a span for the action invocation followed by a span for `run.invokeActions.EXTERNAL_SERVICE` with no child spans beneath it. The absence of child spans under the external service invocation is the diagnostic signature of an MCP or external HTTP call. The trace tree stops at the HTTP boundary because Salesforce instrumentation cannot reach inside the external system.

---

**Topic:** Diagnosing latency in MCP-backed agent actions

**Explanation:** Because Platform Tracing cannot observe internal MCP server execution, latency profiling for MCP actions requires a two-part approach. The first part measures the HTTP boundary: query `ssot__TelemetryTraceSpan__dlm` filtered by the MCP action's operation name and use `ssot__DurationNumber__c` to measure the full round-trip time including both network transit and external server processing. The second part, if available, compares the span duration against the MCP server's own instrumentation logs to separate network latency from server processing time. Without server-side instrumentation the span duration is an upper bound rather than an internal breakdown. For chained MCP callouts where one action triggers multiple HTTP hops, each hop compounds latency at the high-percentile end. Two hops averaging 400ms each can produce a 95th-percentile total that exceeds the sub-2-second voice agent response threshold, which is an architectural concern that best practices recommend flagging for human review.

## Section 6: Dashboards and Analytics

### Objective 6.1: Identify the out-of-the-box dashboard surfaces and the metrics each provides.

---

**Topic:** The Agentforce Analytics Dashboard and its primary metrics

**Explanation:** The Agentforce Analytics Dashboard is the primary out-of-the-box surface for monitoring agent adoption and quality. Its panels include Conversation Volume tracking daily and weekly session counts to monitor the adoption curve after launch; Topic and Intent Breakdown showing which subagents are invoked most frequently, which reveals demand patterns and potential mis-routing; Session Duration tracking average turn count and conversation length as a proxy for resolution complexity; Escalation Rate showing the percentage of sessions handed off to a human agent; Deflection Rate showing the percentage of sessions resolved without human escalation; Sub-agent Invocation Count tracking per-subagent usage trends; and End-to-End Workflow Resolution showing the full session success rate over rolling periods. The Escalation Rate is identified by best practices as the primary quality signal in the first two weeks after a production launch.

---

**Topic:** The Consumption Analytics Dashboard and Consumption Insights Dashboard

**Explanation:** Two additional out-of-the-box dashboard surfaces focus on credit and token consumption rather than quality metrics. The Consumption Analytics Dashboard, powered by Tableau Next, provides panels for Daily Active Users tracking users per agent per day, Input vs. Output Token Breakdown showing token split by direction as a cost optimization signal, Token Usage by User identifying the heaviest consumers and any anomalies, and Usage by Agent for budget attribution across multiple deployed agents. The Consumption Insights Dashboard, powered by Data 360 Reporting, provides more granular data including per-feature and per-model token breakdowns and is the appropriate tool for teams managing Einstein credit budgets across multiple AI products. Neither of these dashboards surfaces quality or routing information; they are cost and adoption tools.

---

**Topic:** Why the escalation rate is the most important early-adoption metric

**Explanation:** The escalation rate is the primary quality signal in the first one to two weeks following a production launch for a specific reason. Test utterances crafted during development, however carefully designed, cannot fully represent the diversity of how real users phrase their requests. The moment real users engage with the agent, they introduce phrasing variations, abbreviations, multi-intent messages, and contextual assumptions that test sessions rarely surface. A spike in escalation rate is the first concrete signal that a category of real user intent is not being handled correctly, and it arrives before users start complaining through support channels or abandoning the conversation channel. Best practices recommend monitoring escalation rate daily for the first two weeks and investigating any increase greater than 20% above baseline by pulling trace files from escalated sessions to identify the common instruction gap or missing subagent coverage.

---

**Topic:** The risk of interpreting raw deflection rate as genuine resolution

**Explanation:** Raw deflection rate as reported by the out-of-the-box dashboard counts all sessions that ended without escalation as deflected, including sessions where the agent responded with a graceful failure message such as "I cannot find your order, please contact support." Sessions that end without escalation are classified as deflected even when the agent failed to actually resolve the user's need. This creates an inflated deflection metric that can give false confidence to stakeholders. Salesforce best practices recommend building a quality-corrected deflection measure by querying `ssot__AiAgentInteractionStep__dlm` to identify sessions where error steps occurred and cross-referencing those against non-escalated sessions. A more robust approach uses a custom `resolved` variable that the agent sets only when a genuine resolution is achieved, then filters the deflection metric to count only sessions where that variable is true.

---

### Objective 6.2: Understand the Data Cloud STDM table model for building custom analytics.

---

**Topic:** The core STDM table set and what each table contains

**Explanation:** When out-of-the-box dashboards are insufficient for a specific analytical need, custom analytics are built directly on the Session Tracing Data Model (STDM) tables in Data Cloud. The core tables are: `ssot__AiAgentSession__dlm` which holds session-level data including start time, end time, and session ID; `ssot__AiAgentInteraction__dlm` which holds interaction metadata including intent, subagent, resolution status, and the TelemetryTraceId for joining to Platform Tracing; `ssot__AiAgentInteractionMessage__dlm` which holds user and agent message content for conversation analysis; `ssot__AiAgentInteractionStep__dlm` which holds action steps with error tracking; `ssot__AiAgentSessionParticipant__dlm` which records agent participation in sessions; `AiAgentGenerativeAiUsage_std__dlm` which records token usage per session; and `ssot__TelemetryTraceSpan__dlm` which holds the back-end execution spans from Platform Tracing. Custom dashboards built on these tables can surface insights unavailable in any out-of-the-box panel.

---

**Topic:** The Einstein Trust Layer Audit Trail DMO tables and when they are available

**Explanation:** The Einstein Trust Layer generates a set of audit trail DMO tables that provide visibility into the LLM prompt and response layer. These tables include `GenAIGatewayRequest__dlm` which captures the compiled prompt sent to the LLM gateway, `GenAIGatewayResponse__dlm` which captures the raw LLM response, `GenAIGeneration__dlm` which holds generation metadata per LLM call, and `GenAIFeedback__dlm` which records user feedback signals such as thumbs up or thumbs down ratings on agent responses. An important distinction from best practices: `GenAIGatewayRequest__dlm` captures the compiled Agent Script prompt, not the user's raw utterance. User utterances must be queried from `ssot__AiAgentInteractionMessage__dlm` where the role field equals "user." These audit trail tables only populate when their corresponding data streams are explicitly enabled in Einstein Trust Layer settings.

---

**Topic:** Proactive monitoring alerts: thresholds, triggers, and interpretations

**Explanation:** Agentforce provides six categories of proactive monitoring alerts. Agent Rate Limit Errors fire when the org-level LLM rate limit is reached, indicating that users are experiencing delays or failures at peak load. Voice Agent Response Failures fire on any spike in TTS or STT pipeline errors, signaling a voice channel SLA breach. Planner Session Start Failures fire when the agent cannot initialize a session, indicating a complete channel outage for affected users. LLM Model Latency alerts fire when response time exceeds a configured threshold, which is especially critical for voice agents where the sub-2-second target must be maintained. Agent Escalation Rate alerts fire at more than 10 fallbacks per 5-minute window, indicating a systemic instruction or routing failure. Error Volume alerts fire at more than 25 errors per 5-minute window, indicating a platform or integration-level issue. All thresholds are configurable, and best practices recommend calibrating them relative to expected traffic volume before go-live rather than leaving them at default absolute values designed for high-volume orgs.

## Section 7: Common Diagnostic Patterns

### Objective 7.1: Apply a systematic diagnostic approach to the most common Agentforce agent failure modes.

---

**Topic:** Pattern A: Wrong subagent routing

**Explanation:** This pattern presents when a user asks about one topic but the agent routes to an incorrect subagent. The diagnostic approach begins at the `LLMStep` in the trace for the routing turn, specifically checking the `tools_sent` field to confirm that all transition actions are listed. If a transition action is absent from `tools_sent`, its `available when` condition is blocking it. If all transition actions are visible but the wrong one was selected, the subagent descriptions are ambiguous or overlap in a way that confuses the model. Best practices recommend inspecting the competing subagent descriptions side by side and adding disambiguation language that explicitly excludes the topic handled by the other subagent. Exclusive phrasing on each subagent description is more reliable than relying on the model to infer the boundary from inclusive descriptions alone.

---

**Topic:** Pattern B: Action not firing despite being expected

**Explanation:** This pattern presents when an agent responds to a request without invoking the expected action. The first diagnostic step is to check the `EnabledToolsStep` in the trace. If the expected action is absent from the enabled tools list, the action's `available when` guard condition is not being met given the current variable state at the time of the turn. The practitioner should cross-reference the guard condition against the `NodeEntryStateStep` to see which variable values were present and identify which condition failed. If the action is listed in the enabled tools but was not called, the action's description does not match the user's phrasing closely enough for the model to recognize it as relevant. The fix in the first case is to relax or restructure the guard condition. The fix in the second case is to strengthen the action description with trigger keywords derived from the actual utterances that should invoke the action.

---

**Topic:** Pattern C: Behavioral loop where the agent repeats the same question

**Explanation:** This pattern presents when the agent asks the same question across multiple turns despite the user having already answered it. The diagnostic approach is to examine repeated `LLMStep` entries across consecutive turns and check the `messages_sent` field for the specific instruction that is triggering the repeated question. The typical root cause is an instruction that evaluates a variable condition rather than checking conversation history. When the variable has not been explicitly set by a prior action, the condition always evaluates as true and the question fires again regardless of what the user said in the previous turn. Best practices recommend restructuring such instructions to treat conversation history as the authoritative source for information the user has already provided, and to use slot-filling patterns with `...` input syntax rather than requiring explicit variable assignment before an action becomes available.

---

**Topic:** Pattern D: Terminal "unexpected error" response

**Explanation:** The message "I apologize, but I encountered an unexpected error" is a specific terminal condition that fires only when grounding fails twice consecutively. A single `UNGROUNDED` result from the `ReasoningStep` gives the model a second attempt. Two consecutive `UNGROUNDED` results trigger the terminal message. The diagnostic approach is to find the consecutive pair of `ReasoningStep` entries both showing `UNGROUNDED` status and examine the `FunctionStep` that preceded them. There are two root causes. In the first, the action executed successfully but the model embellished or paraphrased the response beyond what the data supports. In the second, the action returned an error or empty data, leaving the model with nothing to ground against. The first case is resolved by adding verbatim-usage instructions. The second case is resolved by fixing the backing Apex or Flow to return valid data rather than throwing exceptions on edge-case inputs.

---

**Topic:** Pattern E: Action returns data but the agent's response is generic

**Explanation:** This pattern presents when a `FunctionStep` shows a successful action execution with data, but the agent's reply to the user is generic or does not incorporate the returned data. The diagnostic approach is to examine the `LLMStep` that follows the `FunctionStep` and check the `response_messages` field. If the model invoked a different platform tool or generated a natural language response without referencing the action output, the instructions do not explicitly direct the model to use the specific output fields in its reply. Best practices recommend updating the reasoning instructions to name specific output fields by reference using `{{!@actions.ActionName.fieldName}}` syntax, which creates an explicit connection between the action's output and the expected response content. Generic responses that ignore action data are almost always an instruction authoring gap, not a data retrieval failure.

---

**Topic:** Pattern F: Latency complaint with no visible errors and no failed steps

**Explanation:** This is among the most difficult diagnostic patterns because neither the session transcript nor a surface-level trace review reveals any problem. The agent responds successfully, actions complete with `OK` status, and no error alerts fired. The diagnostic approach requires Agent Platform Tracing to be enabled and then querying `ssot__TelemetryTraceSpan__dlm` with the performance-by-operation-type query to identify which operation type has consistently elevated average duration. Once the slow operation is identified, the practitioner drills into the span attributes for that operation, specifically looking at `db.rows_affected` and `db.operation.name`. A high `db.rows_affected` value such as several thousand rows on what should be a targeted lookup indicates that the backing SOQL query is unfiltered or missing a `LIMIT` clause. The model then receives a large dataset and must process it, creating downstream LLM latency that the session trace records as success while Platform Tracing reveals the data volume problem.

---

### Objective 7.2: Use a structured fix reference to match symptoms to remediation strategies.

---

**Topic:** The fix strategy matrix: mapping symptoms to the correct agent configuration target

**Explanation:** Salesforce best practices provide a structured mapping between observable symptoms and the specific configuration element that should be modified to resolve each one. When a subagent is not matched, the fix target is the subagent's `description:` field, which should be updated to include trigger keywords extracted from the failing test utterance. When an action is not invoked, the fix target is the action's `description:` within the `reasoning.actions` block, which should be made more trigger-specific. When an action is blocked by a guard, the fix target is the `available when:` condition, which should be relaxed or restructured to match the variable state present at the time the action should be invocable. When two actions overlap and interfere with each other, both `description:` fields should be updated with mutual exclusion language. When a grounding failure produces an `UNGROUNDED` result, the fix target is the `reasoning: instructions: ->` block, which should add explicit output references. When a safety score is low, the fix target is the `system: instructions:` block, which should add explicit safety guidelines and scope boundary definitions.

## Section 8: Sandbox vs. Production Observability

### Objective 8.1: Understand the differences in tracing approach and tooling between sandbox and production environments.

---

**Topic:** Key differences between sandbox and production observability configuration

**Explanation:** Observability configuration is not automatically inherited from sandbox to production and must be explicitly managed in each environment. The primary tracing tool in sandbox is the `sf agent preview` CLI, which generates local `.sfdx/` trace files that are ephemeral and practical to review manually given low session volumes. In production, the primary tracing surfaces are the Data Cloud STDM tables and Platform Tracing DMOs, which require SOQL queries to access and represent the only scalable diagnostic approach when session volume is high. Agent Platform Tracing must be enabled separately in each org and does not inherit from any other environment. Alert thresholds are not typically configured in sandbox because it is not a monitored production channel, but they must be configured before any production go-live. Credit consumption occurs in both environments for live action execution, with simulated mode as the only way to avoid credit costs during iterative development.

---

**Topic:** Deploying Platform Tracing configuration via metadata instead of manual Setup UI steps

**Explanation:** Agent Platform Tracing can be enabled as a metadata deployment rather than a manual Setup UI configuration. The `AgentforcePlatformTracingSettings` custom metadata type accepts an `isEnabled` field. Deploying this metadata as part of the same pipeline stage as agent metadata ensures that Platform Tracing is always enabled in target environments without depending on a manual step that may be missed during a go-live deployment. This approach is consistent with Salesforce best practices for configuration that should be treated as code: if a setting affects agent behavior or observability in production, it should be version-controlled and deployed as metadata rather than configured ad-hoc.

---

**Topic:** Transitioning from sandbox trace review to production monitoring

**Explanation:** When promoting an agent from sandbox to production, the observability workflow must change because the tooling that works at low volume does not scale. Best practices recommend a specific transition sequence: first verify that Platform Tracing is enabled in production by confirming the metadata deployment succeeded or the toggle is on in Setup; second confirm Data Cloud DMO accessibility by running the `DataKnowledgeSpace` verification query and checking permission set assignments; third seed baseline metrics during the first 48 hours of production traffic because dashboards need real traffic to establish a baseline before alerts can be meaningfully calibrated; fourth configure all alert thresholds relative to expected traffic volume before the launch date; and fifth transition the team from individual `.sfdx/` file review to SOQL-based STDM queries as the primary diagnostic workflow. The sandbox habit of opening individual trace files does not scale when production volumes reach hundreds or thousands of sessions per day.

## Section 9: Business Value and Cost Management

### Objective 9.1: Translate technical observability metrics into business KPIs and executive-facing outcomes.

---

**Topic:** Mapping technical metrics to business KPIs for executive reporting

**Explanation:** A key practice for practitioners supporting Agentforce deployments is the ability to translate technical observability data into the language of business outcomes that executives and budget owners use. Deflection rate from `ssot__AiAgentSession__dlm` maps to cost-per-interaction reduction for customer service operations. Escalation rate from the Analytics Dashboard maps to agent quality and user trust, which are CX leadership concerns. Action span duration from `ssot__TelemetryTraceSpan__dlm` maps to time-to-resolution and user experience quality, which matter to service operations and IT. Error volume by operation type maps to IT operations efficiency and mean time to resolve. Token usage per session from `AiAgentGenerativeAiUsage_std__dlm` maps to AI cost-per-transaction for finance and budget owners. Safety score distribution from `PlannerResponseStep.safetyScore` maps to brand risk and compliance posture for legal teams. User feedback from `GenAIFeedback__dlm` maps to NPS and user satisfaction for CX leadership.

---

**Topic:** Building a quantitative ROI case using STDM data

**Explanation:** Salesforce best practices outline a repeatable method for quantifying agent ROI using observability data. The first step is establishing the human cost baseline by querying historical case or interaction volume and average handle time for the category of interactions the agent handles. The second step is measuring genuine deflection rate using a quality-corrected query rather than the raw dashboard metric, counting only sessions where an action executed successfully and no escalation occurred. The third step is calculating cost avoidance by multiplying genuine deflections by the difference between the human cost per interaction and the AI credit cost per session. The fourth step is using Platform Tracing latency data to surface efficiency gains from action optimization, expressed as reductions in time-to-resolution. The fifth step is tracking error span trends over time to demonstrate improvements in reliability. Together these five data points constitute a defensible ROI narrative built entirely from observability data.

---

**Topic:** How latency connects to cost-per-interaction as a business metric

**Explanation:** Action span duration from `ssot__TelemetryTraceSpan__dlm` is not purely a performance metric; it is also a cost driver. In voice agent deployments where the sub-2-second response window is the threshold for a natural conversation experience, sessions that exceed this threshold have a measurably higher probability of escalation or abandonment. An abandoned interaction that escalates to a human agent costs significantly more than a genuinely deflected one. Practitioners can quantify this relationship by pulling the distribution of interaction span durations, identifying sessions above the 2,000-millisecond threshold, and cross-referencing those sessions against escalation status in `ssot__AiAgentSession__dlm`. If a strong correlation exists between above-threshold latency and escalation, each 100-millisecond reduction in average span duration translates to a measurable decrease in escalation rate and a corresponding cost reduction. This framing connects infrastructure optimization work directly to the ROI metrics executives care about.

### Objective 9.2: Understand credit consumption patterns and apply cost-aware debugging practices.

---

**Topic:** Credit consumption by operation type and the cost implications of each FunctionStep

**Explanation:** Agentforce credits are consumed per action execution, and understanding the credit model is essential for both cost management and debugging. Framework operations including `@utils.transition`, `@utils.setVariables`, `@utils.escalate`, `if`/`else` control flow, and `before_reasoning`/`after_reasoning` hooks are all free because they execute deterministically without LLM involvement. The LLM reasoning turn itself is also free; the credit cost applies to the actions invoked as a result of reasoning. Flow actions cost 20 credits per execution. Apex actions cost 20 credits per execution. Any other action type also costs 20 credits per execution. Prompt Template actions cost between 2 and 16 credits per invocation depending on complexity. A session with five action executions therefore costs 100 credits in live mode. Simulated preview mode avoids these costs because no real actions execute.

---

**Topic:** Cost-aware debugging practices to minimize credit expenditure during development

**Explanation:** Best practices provide specific guidance for minimizing credit consumption during the development and testing phase. Sim be used for all instruction authoring and routing iteration because it generates fake action outputs at no credit cost. Live preview mode should be reserved for grounding validation, variable-driven branching verification, and final behavioral testing before a go-live decision. An escalation spike alert that fires in production at the threshold of more than 10 fallbacks per 5 minutes represents both a user experience problem and an unplanned credit consumption event if the fallback path involves action retries, because each failed action call still costs 20 credits. Actions that exceed Apex governor limits such as CPU time, SOQL row limits, or heap size appear as `FunctionStep` errors in traces and represent 20 credits consumed per failed call. Optimizing actions to stay within governor limits therefore has both performance and cost benefits.

## Section 10: Roadmap Awareness and Stakeholder Communication

### Objective 10.1: Distinguish between currently available features and roadmap items, and communicate limitations accurately to stakeholders.

---

**Topic:** Features available in the current production Agentforce observability stack

**Explanation:** As of current Salesforce releases, the following observability capabilities are available to production deployments: out-of-the-box Tableau Next dashboards for consumption and agent analytics; session-level trace files generated via the `sf agent preview` CLI; Agent Platform Tracing via `ssot__TelemetryTraceSpan__dlm` requiring manual enablement; Data Cloud STDM tables for custom query-based dashboards and analysis; Einstein Trust Layer audit trail DMOs when the corresponding data streams are explicitly enabled; safety scoring on every agent response accessible via `PlannerResponseStep.safetyScore`; and Slackbot integration for natural language trace queries requiring manual canvas configuration. Practitioners should verify that the features they reference in stakeholder conversations are confirmed available in the current release and not features that are still in preview or on the roadmap.

---

**Topic:** Roadmap items and the current workarounds for each

**Explanation:** Several observability capabilities are on the Salesforce product roadmap but are not yet available as native platform features. Error Rate Metric Splitting, which would break down errors by category such as orchestration failures, handoff failures, authentication issues, and timeouts, is currently approximated by manually querying `ssot__AiAgentInteractionStep__dlm` and categorizing errors based on content. Latency Split Tracking, which would show end-to-end time split by component, is currently approximated by extracting `ssot__DurationNumber__c` from individual spans in `ssot__TelemetryTraceSpan__dlm`. Custom Evaluations using an LLM-as-a-Judge pattern for semantic conflict detection are on the roadmap but currently require custom STDM queries with manual pattern detection. Spend and consumption reporting within the agent analytics dashboard is currently approximated by cross-referencing `AiAgentGenerativeAiUsage_std__dlm` with session data manually. Sentiment analysis and RAG quality metrics are not currently available without custom external pipelines.

---

**Topic:** How to frame roadmap limitations accurately in stakeholder conversations

**Explanation:** When stakeholders ask about capabilities that are on the roadmap rather than currently available, best practices recommend a framing approach that is honest about current limitations while conveying confidence in the current workaround path and the direction of the platform. An effective framing acknowledges what is available today with specificity: real-time escalation rate monitoring, session-level execution traces, and back-end performance profiling down to individual Apex and Flow invocations. It then acknowledges what is coming without committing to a delivery timeline: granular error categorization and latency split reporting by subagent are on the roadmap. Finally it bridges the gap: custom queries against the STDM tables can approximate both capabilities today while the native implementation arrives. This approach maintains credibility with technical stakeholders while setting realistic expectations for what requires custom development versus what will eventually be configuration.
